# 内存占用分析（2026-10-12）

## 一、结论先说

| 现象 | 结论 |
|---|---|
| 后台 105MB / 打开设置 150MB | 实测（私有提交）：仅主窗口 ≈ 179MB，打开设置 ≈ 244MB。你看到的数字是任务管理器的「专用工作集」，比提交小 |
| 内存是不是泄漏了 | **不是**。实测 85 秒采样平稳在 164MB，无增长 |
| 关掉设置 / 主窗口为什么不降 | **销毁几乎拿不回来**：销毁交换链回 0.5MB，销毁 Vulkan 设备回 46MB，**销毁全部之后仍留 97MB**——这部分在显卡驱动的池里，进程活着就拿不回 |
| 便宜的部分 | 中文字体每个窗口各装一份（≈14MB/份）；改为进程级共享后，设置窗口的额外开销从 **+65MB 降到 +25MB** |

## 二、逐阶段账目（实测，私有提交）

`RUST_LOG=...,mem=info` + `crate::mem::trace_stage` 打点，debug 构建：

| 阶段 | 私有提交 | 增量 |
|---|---|---|
| 进程刚起来 | 2.7 MB | — |
| Win32 窗口 + 事件循环 | 2.7 MB | +0.0 |
| `Gpu::new`（Vulkan 实例 + 设备） | 60.5 MB | **+57.8** |
| 渲染通道 / 描述符布局 / 管线布局 / 着色器 / 图形管线 | 62.2 MB | +1.7 |
| `FrameRenderer::new`（**交换链**） | 143.5 MB | **+81.3** |
| `Painter::new` | 144.6 MB | +1.0 |
| `App::new`（egui Context + 中文字体） | 153.0 MB | +8.3 |

对照：**只跑 MCP 服务**（`modular-clipboard --mcp-http`，无任何窗口）**2.3 MB**。
即：核心逻辑（存储 / 剪贴板捕获 / MCP）几乎不占内存，多出来的 150MB 全在「窗口 + GPU + egui」这条链路上。

窗口尺寸几乎不影响总量（520×800 → 240×320 只差 4MB），说明开销不是随分辨率伸缩的交换链图像，
而是**驱动侧的固定开销**。

## 三、销毁能拿回多少（判定探针）

`cargo run -p modular-clipboard-gfx --example mem_drop_probe`（本仓自带，可复现）：

```text
0 起点                     private_mb=   2.0
1 窗口已创建                private_mb=   2.6
2 Gpu::new（设备）          private_mb=  60.2   (+57.6)
3 管线对象齐了              private_mb=  61.9
4 FrameRenderer（交换链）   private_mb= 143.0   (+81.1)
5 只 drop FrameRenderer     private_mb= 142.5   (-0.5)   ← 交换链销毁几乎不归还
6 管线对象已显式销毁         private_mb= 142.5   (0.0)
7 Gpu 已销毁（设备+实例）    private_mb=  96.7   (-45.8)  ← 只有销毁设备才回一部分
8 销毁后等 1.5s             private_mb=  96.7
```

**含义**：驱动（本机 NVIDIA RTX 5070 Laptop / AMD 核显双显卡）在第一次用到 Vulkan 时就建立自己的内存池，
之后无论我们怎么销毁，约 95MB 一直留在进程里。这是驱动行为，不是本项目的代码问题，也**不能**通过
「把对象 drop 掉」解决。

> 探针里还有一个真 bug 被这轮发现并修掉：`GraphicsPipeline` / `ShaderModule` / `PipelineLayout` /
> `DescriptorLayout` **没有实现 `Drop`**，写 `drop(pipeline)` 是空操作（clippy 会警告），
> 必须显式 `destroy(&device)`。早前的 `draw_probe` 是对的，`mem_drop_probe` 初版写错了。

## 四、本轮已做的优化

1. **字体字节进程级共享**（`theme::shared_font_data`）
   `FontDefinitions::font_data` 存的是 `Arc<FontData>`，缓存同一份即可让所有 `egui::Context`
   共用一份中文字体字节。效果：设置窗口的额外开销 **+65MB → +25MB**。
   单测 `theme::tests::font_bytes_are_shared_between_contexts` 守着「同一路径取到同一个 Arc」。

2. **设置窗口关闭即销毁**（`app::drive_attach_windows`）
   早前关闭只是 `SW_HIDE`：窗口、它自己的 `egui::Context`、交换链全部**永久留着**。
   现在关闭 = `*settings_win = None`，由 `Drop` 连 `vk::SurfaceKHR` 一起释放（`Drop` 实现已存在）。
   实测关闭后回落 3MB —— 印证了第三节：GPU 侧的池拿不回来，CPU 侧能拿回的已经不多
   （字体共享后这部分本来就变小了）。真正受益的是**不再累计**：反复开关不会一层层往上堆。

## 五、剩下的三条路（按收益排序）

### 路线 A：UI 会话按需创建 / 隐藏即销毁（中等改动）

把「窗口 + GPU + egui」整体包进一个可反复创建销毁的会话：

- 启动即后台时不建窗口/不建 GPU ⇒ 后台 ≈ 5–10MB（现在是 165MB）；
- 窗口隐藏到托盘 ⇒ 销毁整个会话 ⇒ 回落到约 97MB（现在 179MB）；
- 代价：每次唤起要重建一次 GPU 栈，实测初始化到首帧约 **0.4 秒**（从启动日志的时间戳算出：
  `启动 → 渲染器就绪 + 字体`）；且需要对 `run()` 做大范围结构调整（托盘要提到会话之外常驻）。

### 路线 B：UI 独立进程（收益最大，改动最大）

后台服务进程只跑存储 / 捕获 / MCP（实测 **2.3MB**），UI 进程按需拉起、关闭即退出。
关窗时内存**百分之百归还**——这是 Windows 上唯一能真正把 GPU 侧内存还给系统的办法。
代价：需要跨进程通信（命名管道 / 本地 socket）与一套「UI 不在时也要能响应热键」的机制。

### 路线 C：接受现状

150MB 对于一个常驻工具偏高，但其中约 95MB 是驱动固有占用，任何 Vulkan 程序在这台机器上都要付。
若不再扩展功能，C 也是可选项。

## 六、怎么复现本轮结论

```bash
# 1. 逐阶段账目（需要带打点的构建）
RUST_LOG="warn,modular_clipboard=info,mem=info" ./modular-clipboard
# 2. 销毁能否归还
cargo run -p modular-clipboard-gfx --example mem_drop_probe
# 3. 不带界面的地板值
./modular-clipboard --mcp-http     # 2.3MB
```

## 七、路线 B 已落地（2026-10-12 晚）

用户选了路线 B。实现方式：**界面与后台拆成两个进程**，
之间用 Windows 命名管道传「状态 + 命令」。

### 7.1 进程分工

| 进程 | 启动方式 | 做什么 | 不做什么 |
|---|---|---|---|
| 常驻进程 | 默认（双击）/ `--daemon` | 监听剪贴板、存历史、托盘、全局热键、IPC 服务端 | **不建窗口、不初始化 Vulkan** |
| 界面进程 | 由常驻进程拉起 / `--ui` | 建窗口、渲染、显示列表 | 不打开数据库、不监听剪贴板、不建托盘 |

向后兼容：`--single` 保留旧的单进程行为，排查问题时更好调。

### 7.2 关键设计

1. **`Service` 加了一层后端抽象**（`Backend::Local` / `Backend::Remote`）。
   界面侧代码几乎不用改：它照旧调 `svc.reload_list()` / 读 `svc.state.items`，
   由 `Service` 内部决定是本进程执行还是发命令给常驻进程。
2. **界面每帧一次增量同步**。常驻进程维护一个数据版本号，
   版本没变时回答 `{"Unchanged"}`（几十字节）——所以「每帧问一次」
   不会把两千条历史反复序列化。
3. **写命令顺带带回新列表**。改完（增/删/置顶/清空）常驻进程直接把
   新快照塞进响应里，省掉界面「改完再问一次」的往返。
4. **`Service` 不是 `Send`**（SQLite 连接），所以 IPC 线程只做收发，
   请求转回主线程执行。副作用是请求天然串行，界面看到的状态永远一致。
5. **界面失联即自退**：常驻进程被杀/崩溃后，界面检测到同步失败会自己退出，
   而不是留一扇永远不更新的窗口。
6. **单实例语义跟着拆**：常驻进程持有全局互斥体；界面进程持有自己的
   `UiInstanceGuard`。用户重复双击图标 ⇒ 第二个进程连上 IPC 发 `ShowWindow`
   ⇒ 常驻进程「界面没跑就拉起、跑着就唤到前面」。

### 7.3 实测（本机 debug 构建，任务管理器「内存」列）

| 场景 | 改造前（单进程） | 现在 |
|---|---|---|
| 后台常驻（界面未打开） | 105 MB | **15–16 MB** |
| 界面打开时 | 150 MB | 常驻 21 MB + 界面 174 MB |
| 关掉界面之后 | 150 → 130 MB（GPU 池不归还） | 常驻 **21 MB**，界面进程整块消失 |

界面进程的 174MB（debug）里大头仍是 Vulkan 设备 + 交换链 + 字体图集；
差别在于**它随进程一起消失**——这是 Windows 上唯一能把 GPU 池内存
真正还给系统的办法（路线 A 做不到：销毁只是把内存丢进驱动自己的池子）。

### 7.4 端到端验证记录

```
启动 --daemon            → 进程 1 个，14.9 MB，日志「捕获线程已启动」
Set-Clipboard 两次       → 库里出现 2 条（source_app=msedge）
启动 --ui                → 进程 2 个，界面 174 MB
杀掉界面进程             → 界面进程消失，常驻仍在 21 MB
再跑一次 exe（无参数）   → 第二个进程退出码 0，常驻日志「已启动界面进程」，界面重新出现
再跑一次 exe（界面已在） → 进程数仍是 2（被唤起，而不是重复启动）
杀掉常驻进程             → 界面在数秒内自行退出（失联检测生效）
```

### 7.5 新增/改动的关键文件

- 新 crate `modular-clipboard-ipc`：协议（`protocol.rs`）、命名管道（`transport.rs`）、
  客户端（`client.rs`）、服务端（`server.rs`）、实例发现与唤起（`instance.rs`）。
- `modular-clipboard-app`：`Service` 拆双后端（`lib.rs`）、新增常驻进程入口（`daemon.rs`）。
- `modular-clipboard-ui`：`App::from_service` / `run_remote`，远端模式不建托盘、关窗即退。
- `modular-clipboard`（bin）：`--daemon` / `--ui` / `--single` 三种角色。

### 7.6 已知取舍

- 界面首帧比单进程多一次 IPC 握手（本地管道，毫秒级）。
- 联动动作（`run_action`）与自动粘贴在界面侧暂不支持——它们需要动作注册表，
  而注册表在常驻进程手里。界面目前用不到这两条路径。
- 协议带版本号：升级后若旧常驻进程还在跑，新界面会明确报
  「协议版本不一致，请退出旧进程后重试」，而不是静默错乱。
